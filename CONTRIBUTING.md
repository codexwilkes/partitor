# Contributing

Helpful pull requests are welcome. The maintainer supports what he can test:
Ubuntu LTS on x86-64 with systemd. Other platforms are best effort.

## Where things are

| File | About |
|---|---|
| `docs/DESIGN.md` | Rules and algorithms (section numbers are stable) |
| `docs/SANDBOX.md`, `SECURITY.md` | What the sandbox does; reporting problems |
| `docs/LIBRARY-LAYOUT.md` | The stable folder and file-name contract, for tools that publish or read the library |
| `docs/OVERLAYS.md` | Wrap the installer for a site (unsupported sample) |
| `platforms/windows/README.md` | Experimental Windows console build and installer (not supported) |
| `docs/ARCHITECTURE.md` | How the program is built, with diagrams (diagram as code; the module block is generated by `tools/check-architecture.py --write`; the gate checks it) |
| `docs/COMMANDS.md` | Every command and option (generated by `tools/build-cli-doc.py`; do not edit) |
| `docs/RELEASING.md` | Version numbers, pre-releases, what a tag must contain |
| `CHANGELOG.md`, `NOTICE` | History, third-party licences |

## Rules

- **One change, one pull request.** Say what and why.
- **CHANGELOG.md**: every code change gets an entry under the next version
  (SemVer). Mark breaking changes `BREAKING`. A change to `docs/LIBRARY-LAYOUT.md`
  goes under "Library layout".
- **Tests**: every code change has tests. The number of tests must not fall.
  Compare counts in the same environment: corpus tests need your own PDFs and
  skip without them.
- **Docs match the code.** A document that contradicts the code is a defect.
  When you change behaviour, search `README.md` and `docs/` for the old text and
  fix it in the same pull request.
- **SPDX header** in every file under `bin/`, `lib/`, `tests/`, `tools/`:
  `SPDX-License-Identifier: AGPL-3.0-or-later`. Your contribution is under the
  same licence.
- **No scores, scans or personal data** in the repository, not even one page.
  Tests draw synthetic PDFs. `tools/check-repo.sh` checks this.
- **No private addresses or host names** in code, docs or tests. Use
  `192.0.2.x` or `example.net` for examples.
- **Section numbers** in `docs/DESIGN.md` are stable: the code cites them. Add
  new text as a new subsection.
- Keep English plain and short.

## Add a choice (a user setting)

Add a choice only when the right answer depends on the player's equipment or
habit, not on the score. Keep the old behaviour as the default, so an item
built before the choice builds the same.

- One lowercase key. Use an enum (`dotted | marks | off`), not a boolean, when a
  third value is plausible.
- Put it in `LAYOUT_DEFAULTS` (`lib/partitor/config.py`) and describe it in
  `LAYOUT_HELP` there.
- Put it in `SET_KEYS` (`lib/partitor/library.py`), so `partitor set` accepts it.
- Add a `--flag` in `lib/partitor/cli_main.py` only for a build option.
- Pass it where it acts (read it with `opts.get(key, default)`).
- Name it in `docs/DESIGN.md`, and add a CHANGELOG entry.

`tests/test_choices.py` fails when an enum key misses `SET_KEYS`,
`LAYOUT_HELP` or `docs/DESIGN.md`.

## Run the checks

CI (`.github/workflows/ci.yml`) runs the same checks on every pull request:
the repo gate, shellcheck at warning level, and the tests on Ubuntu 24.04
(Python 3.12 and 3.13). The macOS run is best effort and does not block.
CI keeps the pip wheels between runs (`cache: pip`).

A test class that needs a built item builds it once, in `setUpClass`, and copies the
built folder for each test (`_PagesItem` in `tests/test_render.py`). A detect and a build
take 25-60 s; one per test made `test_render` the slowest module.

```bash
cd /opt/partitor      # or your clone
venv/bin/python3 -m unittest discover -s tests -v
tools/check-repo.sh                           # also runs tools/check-modules.py --static and tools/build-operator-doc.py --check
shellcheck -S warning bin/partitor bin/partitor-init bin/partitor-install tools/check-repo.sh tools/bench-start.sh   # if installed
```

While you work, run only the tests of the files you touch, for example
`venv/bin/python3 -m unittest -v tests/test_clef.py`. Run the full suite before
you open the pull request.

To run the full suite faster on your machine, use `tools/test-parallel.py`. It finds the
tests as CI does, runs them in 4 processes (`--jobs N`) and fails when a test fails, a process
dies or the number of tests that ran differs from the number found. It splits by test class,
using the seconds in `tools/test-weights.txt` (a class not listed counts 0.05 s per test; the
numbers only balance the load). It needs about 2 GB more memory than a serial run. More than 4
processes was slower on 8 cores. CI stays serial (`unittest discover -s tests`).

The operator guide `docs/operator-flow.html` is generated. Edit `docs/operator/guide.md`,
`docs/operator/problems.md` or `docs/operator/operator.css` (rules: `docs/operator/README.md`), then run
`tools/build-operator-doc.py` and commit the result with the sources. Run it again when `VERSION` changes.
The tool needs `markdown-it-py` and `PyYAML` on the developer machine only
(`sudo apt install python3-markdown-it python3-yaml`); users need nothing new.
A new key in `item_menu` (`lib/partitor/cli_main.py`) needs a row in the item-menu table of `guide.md`:
a test compares the two.

Corpus tests (slow): `PARTITOR_CORPUS=/path/to/folder venv/bin/python3 -m
unittest -v tests/test_analysis.py`. The folder holds your own PDFs with the
names in the `CORPUS` table of `tests/test_analysis.py`.

For a refactor of the engine, record and check golden renders with
`tools/g0_golden.py` (`DESIGN.md` §10; `--timings` shows where the time goes; a changed page
is written as an image next to the golden).

Real pages: a scan page that showed a defect can join a folder outside the repo (`PARTITOR_REAL_PAGES`,
`DESIGN.md` §10). Add an entry to its `corpus.yaml` (`item`, `page`, a neutral `name`), run
`tools/real-pages.py extract`, then `probe --png DIR`, look at the picture, and write the `expect`
only for what you checked by eye. The values say what the engine does now, not that it is right.

## Where does my change go

The engine is the package `lib/partitor/` (`DESIGN.md` §12); `lib/partitor-engine` is only the
launcher that starts `partitor.cli_main.main`. A change goes into the module that owns the
name. The 29 modules and their import levels:

| Lvl | Module | Put here |
|---|---|---|
| 0 | `console` | Output, colours, prompts |
| 0 | `config` | Tunables, defaults, paper sizes, name helpers |
| 0 | `model` | Data classes |
| 0 | `hooks` | Platform seam (Linux defaults) |
| 0 | `outfile` | Output writes, clear error |
| 0 | `typography` | Fonts, text measure |
| 0 | `mapping` | Staff label to part map |
| 0 | `bars` | Bar numbers, barline edits |
| 1 | `vision` | Page render, staff and system detect, OCR |
| 1 | `clef` | Clef signature, ambitus |
| 1 | `parallel` | `fork_map`, job sizing |
| 1 | `reflow` | Re-flow of strips |
| 1 | `strips` | Strip build, bar marks, rehearsal boxes |
| 1 | `turnplan` | Page-turn planner: spreads, fold-outs, turn classes |
| 1 | `runlog` | Run log of one CLI run (off by default) |
| 2 | `ownership` | Ink ownership, safety gate |
| 2 | `lines` | Line fitting, multi-bar rests, saved lines |
| 2 | `stagecache` | Stage cache of the page analysis |
| 3 | `analysis` | Page loop, preview |
| 3 | `render` | Packing, part drawing |
| 4 | `partplan` | Part planning: options of a part (paper, staff size, page turns) |
| 4 | `library` | Item folder, ids, load and save, `step_size` |
| 5 | `build` | `pieces`, `detect`, `build` |
| 5 | `proof` | Proof PDF |
| 6 | `cli_common` | Shared CLI helpers |
| 7 | `cli_bars` | `bars` command |
| 7 | `cli_parts` | `parts`, `groups` commands |
| 8 | `cli_items` | Item commands |
| 9 | `cli_main` | Menu, `main` |

Rules (`tools/check-modules.py` checks them; CI runs it):

- A module imports only from a **strictly lower** level, never in a cycle. Every module
  starts with `from __future__ import annotations` and the SPDX line.
- **R1:** use state that other modules rebind, and every name in `tests/patchable.txt`,
  as `module.NAME`. Do not write `from module import NAME`: it makes a copy, and a test
  patch or a rebinding then changes only the owner. An object that is only changed in place
  (a counter dict, a list) may be imported by name; both names are the same object.
  `global NAME` is allowed only for a name that the same module defines.
- **Image libraries:** the modules that `list`, `show`, `set` and the other item commands
  use must not import cv2, numpy or pymupdf at the top. Import the package inside the
  function that uses it, and a heavy module (`build`, `render`, `analysis`) inside the
  function of the command that needs it (`DESIGN.md` §12.3; `tests/test_lazy_imports.py`).
- **A new patchable name:** when a test replaces a name with `mock_attr` or an
  assignment on `pt`, add the name to `tests/patchable.txt` (one per line) in the same
  change, and make the readers use `module.NAME`.
- At most 1 100 definition lines per module.

Commands:

```bash
python3 tools/check-modules.py --static     # the rules above; no package needed
venv/bin/python3 tools/check-modules.py --import   # each module imports alone
python3 tools/check-modules.py --affected clef     # modules that import clef, and the tests to run
```

`--affected` prints the modules that import the module (also through other modules)
and the test files of those modules and of the module itself (`tools/modules.txt`);
`*` means all tests.

Saved `.lines` files: the reader accepts the class paths of every earlier layout
(`__main__`, `partitor.*`); do not narrow it. The fixture `tests/data/lines-0.4.2.lines`
was written by the engine before the first move, and a test loads it. Binary fixtures in
`tests/data/` carry no licence line (`tools/check-repo.sh` skips that folder for this check).

## Windows and macOS

Linux is the primary system; production runs on it. Windows and macOS are best effort
(`DESIGN.md` §12.6).

- Work for a platform goes into its pack, `platforms/<os>/`: code, build script, tests and docs.
  Do not change `lib/partitor/` for one platform.
- A change goes into the core only when it is better for every system, Linux included. Send it as
  its own pull request; it must pass the Linux checks.
- If a pack needs a new hook in `lib/partitor/hooks.py`, send the hook and its Linux default as a
  separate, small pull request first.
- Docs for one platform stay in its folder (`platforms/<os>/README.md`). The docs in `docs/` and
  `README.md` only point to them.

## Version

The version is in `lib/partitor/__init__.py` (the engine reads it) and in the file
`VERSION` (the wrapper and the installer read it). A test checks that they agree.
The maintainer sets it at release.

## Support

Best effort. The maintainer does not log in to your systems. Open an issue with
the output of `partitor --version`, your Ubuntu version, and the failing line.
Security problems: `SECURITY.md`.
